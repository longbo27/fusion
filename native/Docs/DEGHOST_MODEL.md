# FocusMotionNetV1

V2.2 uses a compact encoder/decoder with 16/32/48-channel stages, two stride-2 reductions, nearest-neighbor upsampling, convolution/ReLU skip decoders, and 124,327 parameters. Fixed 1×12×256×256 input and 1×7×256×256 output support bounded native-scale execution. A 24px context halo leaves a 208px core; patch starts remain aligned with the stride-4 network. The production model predicts masks and captured-source probabilities, never RGB.

Inputs are reference/best/second/third encoded luminance, two reference residuals, normalized local residual, photographic focus confidence, reference edge, top-label disagreement, Welford temporal standard deviation and temporal range. Only top-three luminance/indices and scalar statistics persist as frames stream through the existing Metal focus pass. Source count does not size a tensor, RGB collection, pyramid or queue. macOS and iOS share model and shader resources.

The final training feature contract calls the unchanged Python golden `photographic_score(..., quality='max')`, quantizes to UInt16 and matches native reflect101 local/edge features. An initial gradient-ranking proxy caused a measured end-to-end mismatch and was replaced. The developer tools invoke Python only for training/fixtures/validation; the application never invokes Python.

Synthetic categories cover grass, leaves, branches, hair, flowers, cloud, water, waves, cloth, occlusion, blurred silhouettes, static defocus, bokeh and noise. Static perturbations include spatial defocus, focus-resampling residuals, exposure, local contrast, softness and chromatic-fringe approximation. Moving layers include subpixel shifts, deformations and occlusion; blur support expands reliable synthetic motion labels. These approximations do not substitute for a photographic dataset.

Training used an isolated existing PyTorch 2.7.1/coremltools 9 environment and a capped MPS allocator. Stages were 4000 base +2000 hard steps, 3000 balanced hard steps, then 1500 base +3000 hard steps with corrected photographic features. Final mining examines 600 independent generated candidates, retains the worst 160 eligible static examples, and mixes them with new motion examples. Seeds 2201/2205001/2207001/2211001 separate training, mining, model validation and native-policy validation. Metadata records stage provenance, mining results and final checkpoint/weights hashes. Earlier gradient-proxy warm starts are historical; a fresh run of the current corrected trainer is not asserted bit-identical to this checkpoint. MPS/library versions also affect reproducibility.

Core ML conversion uses ML Program, macOS14/iOS17, Float16 internal **mask-model** weights/operations with Float32 input/output. Photographic Metal processing remains Float32 and TIFF remains RGB16. All four compute configurations and the actual Metal ML package pass the external PyTorch fixture within a documented .02 probability tolerance (maximum observed .013389 on CPU). This tolerance concerns mask inference, not RGB accuracy. Compute-plan preferred/supported device labels are exposed diagnostics; they do not constitute a physical operation trace.

`MotionInferenceSession` probes CPU, CPU+ANE when enumerated, `.all`, and CPU+GPU sequentially, validates shape/range/numerical agreement on a bounded calibration fixture, and chooses the fastest validated warm median. It retains at most the current candidate and winning model. Unsupported configurations are reported and skipped. A supplied compatible Metal ML package adds a measured backend with persistent tensors, heap and argument table and event-ordered GPU copies; it can win or fall back to ordinary Core ML. The app ships the portable Core ML source package; compiled Metal packages are SDK/platform-specific external developer artifacts, not bundled binaries. A live Metal failure falls back to the retained Core ML model and updates diagnostics. Calibration timings vary with warm caches and device load.

Native policy uses Auto motion ≥.90/safety ≤.10/ownership confidence ≥.75; High ≥.65/≤.35/≥.65. Neighborhood support preserves confident thin centers, followed by a one-native-pixel boundary expansion and GPU component grouping. Each detected component currently chooses captured source 0 consistently. Ownership logits are available but do not yet authorize a different component source. Consequently a blurred reference can sacrifice local focus; photographic source-choice training is still needed.

The original static ownership/pyramid is preserved. Final strong-motion projection selects captured reference RGB and annihilates the complete reconstructed Laplacian sum, including every coarse level. This prevents ghosts without changing pixels outside the mask through changed coarse weights. An injected-mask test and 168 native-policy scenes measure exact RGB16 equality outside detected masks. Final projection is intentionally hard with a one-pixel protected boundary; broader transitions and component quality choices remain future work.

`Developer/Deghost/annotations.py` supports external 256/512 crops, static/moving/ignore polygons and captured preferred-source labels. Unlabelled pixels stay ignore; source indices absent from a candidate set stay unknown. `reviewed:true` is human review, never assigned automatically. Original-stack groups cannot span train/validation. The local Hasselblad stack is reserved for validation; the executed annotation preparation is **unreviewed** and no real labels or real training examples were used. Source previews are explicitly RGB16→8-bit diagnostics only.

Use the existing training venv and reference cv2 ABI through `run_with_reference.py --reference-site ... train|quality|annotations`; no dependency is installed in or changed for the reference engine. All training checkpoints, fixtures, private crops, logs and compiled models remain external. `quality.py --generate`, native benchmark `--deghost-quality`, then `quality.py --evaluate` measures the actual GPU/Core ML/regularization/fusion path. `compare_proto.py` evaluates the original pairwise prototype contract and original .97/.85 operating thresholds on the same crops. Quality comparison uses PyTorch CPU for the old prototype and does not claim a hardware latency comparison.

See [V2.2 results](V2_2_RESULTS.md) for per-category metrics and explicit target misses. This model is production-oriented infrastructure with measured improvements, not a claim that production photographic deghost quality is solved.
